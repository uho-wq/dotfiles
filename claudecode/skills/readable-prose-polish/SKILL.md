# 推敲ループ

書き手は自分の文章を客観視できない。書いた直後は特に。だから評価を別コンテキストのエージェントに出す。critic には会話の経緯を渡さないので、「前提を知らない読み手」に最も近い視点で読まれる。

## 手順

### 1. 下書きを書く

`readable-prose` skill（必要なら `structured_output` も）に従って普通に書く。ループがあるからと雑に書かない。初稿の質が低いとループ回数が増えるだけ。

### 2. 評価パケットを作る

critic に渡すのは次の2つ**だけ**。

- 読み手と目的の1行（例:「読み手: 他チームのSRE。目的: 障害の原因と対応の報告」）
- 文章の全文

会話の経緯・技術的背景・自分の意図の説明を渡さない。「これは〜という事情があって」と補足したくなったら、その事情は文章に書かれているべき情報。

### 3. critic に投げる

Task tool で `readable-prose-critic` エージェントを起動し、評価パケットを渡す。

### 4. 指摘を反映する

- **must-fix**: 原則すべて反映する。ただし反映すると事実が変わる・情報が減る場合は反映せず、却下理由を1文で記録する。critic は内容の正誤を知らないので、事実に関わる判断は書き手側の責任
- **nice-to-have**: 同意できるものだけ反映する。迷ったら反映しない
- 指摘箇所だけを直す。指摘されていない箇所を巻き添えで書き換えない（新しい欠陥を持ち込む典型パターン）

### 5. 再評価する

修正後の全文で手順2〜4を繰り返す。

**終了条件（どれか1つで終了）:**

- VERDICT が PASS
- 3周した（初稿評価＋再評価2回）
- must-fix の全件が「事実が変わるため却下」になった

3周して PASS しなかったら、そのまま出してよい。最終出力に未解決の指摘を1〜2行で添える（例:「critic は◯◯の指摘を残しているが、正確さを優先してこのままにした」）。

### 6. 出力する

最終版の文章を出す。ループの過程（何周したか、何を直したか）は報告しない。ユーザーが知りたいのは文章であって推敲ログではない。ただし手順5の未解決指摘の注記だけは残す。

## ループを腐らせないための注意

- **critic の指摘は命令ではない。** 事実・正確さ・削ってはいけない情報（readable-prose §6）と衝突したら書き手が勝つ。critic に気に入られるための書き換えは目的の逆
- **振動したら止める。** 直した箇所が次の周で逆方向に指摘されたら、それは好みの往復。その指摘は却下してループを閉じる
- **傾向は資産にする。** critic の「傾向」欄に同型パターンが出たら、最終報告の後に `/readable-prose-add` での登録をユーザーに提案する。ループの学習を skill 本体に還流させるのがこの仕組みの本命

## コスト感覚

1周ごとにサブエージェント1回分のトークンを使う。Slackの一言返信や相槌に回すものではない。「この文章は複数人に読まれる／後で読み返される」が発動の目安。
