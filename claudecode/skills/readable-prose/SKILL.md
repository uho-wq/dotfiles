# 伝わる文章

読み手は最後まで読まない。だから答えを先に置き、各文を一読で理解できる形にする。

このskillが扱うのは**文レベル**。全体の構造設計とHTML出力は `structured_output` skill の担当（§7）。

---

## §0 唯一の絶対ルール — 結論ファースト

**冒頭の1文が答えになっていること。** 背景・経緯・前提は、答えの後に置く。

- 質問には Yes / No / 数値 / 固有名を最初に出す
- 「調べたところ」「〜を確認した結果」で書き始めない。それは作業の順序であって、読み手が知りたい順序ではない
- 「結論から言うと」は不要。結論を先に書けば、そう宣言する必要がない

**Before**

> ログを確認し、次にコネクション周りを調査しました。その結果、プール設定が最大10であることが判明し、深夜帯のアクセス集中時にこれを超過していることが分かりました。したがって、原因は接続プールの枯渇であると考えられます。

**After**

> 原因は接続プールの枯渇です。上限が10で、深夜帯のアクセス集中時にこれを超えて待機が発生していました。

読み手が最初の1文で離脱しても要点は伝わる。これが結論ファーストの目的。

## §1 文の設計 — 一文を読み間違えさせない

### 1. 一文一義

1つの文に主張は1つ。「〜であり、〜のため、〜となります」と連なったら、そこが文の切れ目。

### 2. 文頭に既知、文末に新情報

前の文に出た語で書き始めると、読み手は接続先を探さずに済む。新しい情報は文末に置く。文末は読み手が最も強く印象に残す位置。

- ✗ `verifyToken` を `auth.ts` に追加しました。JWTの署名検証と有効期限チェックを `verifyToken` は行います。
- ○ `auth.ts` に `verifyToken` を追加しました。`verifyToken` が担うのは、JWTの署名検証と有効期限チェックです。

### 3. 主役を主語に、動作を動詞に

名詞化（「〜を行う」「〜が可能」）は動作を名詞に閉じ込め、主語を消す。動詞に戻すと「誰が何をするか」が一読で分かる。

| 名詞化 | 動詞 |
| --- | --- |
| 実装を行う | 実装する |
| 削減が可能です | 削減できます |
| 検証の実施 | 検証する |
| エラーの発生が確認された | エラーが出た |

### 4. 主語と述語を離さない

主語と述語の間に長い修飾が挟まると、読み手は述語に着くまで主語を保持し続ける。挟まる要素は前に出すか、文を分ける。

### 5. 一文は40〜60字を目安に

80字を超えたら分割を検討する。ただし全部を短くすると単調になる。長短を混ぜる。

### 6. 確信度を書き分ける

断定・推測・未確認を混ぜない。ヘッジ（「〜かもしれません」「〜と思われます」）を全文に一律で付けると、どれが確かでどれが不確かか読み手に判別できない。

- 確認済み → 「〜です」（必要なら根拠を添える）
- 未確認の推測 → 「おそらく〜。ただし未確認」
- 分からない → 「分かりません」とそのまま書く

### 7. 抽象語を具体に置き換える

「適切に」「効率的に」「最適化」「改善」は、それ自体では情報量がゼロ。何をどうするかを書く。

- ✗ エラーハンドリングを適切に行います
- ○ 400番台はそのまま返し、500番台はリトライします

## §2 日本語固有の語順と読点

日本語は語順が自由な分、順序を誤ると係り受けが曖昧になる。

### 修飾語の順序（優先度の高い順）

1. **節を先に、句を後に**
2. **長い修飾語ほど先に、短いほど後に**
3. **大状況・重要なものほど先に**
4. **親和度の強い語どうしが隣り合うと誤読を招くので、離す**

長い修飾語を先に出す例:

- ✗ `retryClient` は3回まで、指数バックオフでリトライしたうえでタイムアウトした場合に、エラーを返す。
- ○ 指数バックオフで3回までリトライしたうえでタイムアウトした場合、`retryClient` はエラーを返す。

親和度による誤読の例:

- ✗ 新しいトークンを発行するエンドポイントのテストを追加した。（「新しい」がトークン／エンドポイント／テストのどれにかかるか不明）
- ○ トークンを発行するエンドポイントに、テストを新しく追加した。

### 読点を打つのは2箇所だけ

1. **長い修飾語が2つ以上あるとき、その境界に打つ**
2. **原則的な語順を崩して逆順にしたとき、その位置に打つ**

「息継ぎ」「なんとなく読みやすいから」で打たない。読点は係り受けを示す記号であって、リズムの記号ではない。

### その他

- 「が」を逆接以外で使わない（「確認しましたが、3件ありました」→「確認したところ、3件ありました」）
- 二重否定を使わない（「実行されないわけではない」→「実行される」）
- 動作主が分かるなら受身にしない（「設定が読み込まれる」→「起動時に設定を読み込む」）

## §3 段落と見出し — 読み手はスキャンする

読み手は全文を読まない。上から拾い読みしても筋が通るように書く。

- **段落の先頭文を、その段落の要約にする。** 先頭文だけを縦に読んで意味が通るのが理想。
- **見出しはラベルでなくメッセージにする。** 「## 変更点」ではなく「## レスポンス形式が変わる」。
- **箇条書きは並列なものだけ。** 粒度と種類をそろえる。原因と対策を同じリストに混ぜない。
- **事実・意見・推測を書き分ける。** 「ログにこう出ている」（事実）と「だから〜が原因だ」（意見）を同じ調子で並べない。

## §4 AI文章の癖 — 書いたら消すリスト

以下は情報を1ビットも運ばない。書いてしまったら消す。

**前置き**
- 「承知しました」「かしこまりました」
- 「〜についてご説明します」「以下に示します」
- 「結論から言うと」

**締め**
- 「以上、参考になれば幸いです」
- 「何かあればお知らせください」
- 「引き続きよろしくお願いします」

**中身のない強調・列挙**
- 「重要なのは〜という点です」
- 「〜が挙げられます」（→「〜です」）
- 「〜という点で〜です」
- 無理に3つ挙げる（材料が2つなら2つでいい）

**冗長・名詞化**
- 「〜を行う」「〜を実施する」
- 「〜することができます」（→「〜できます」）
- 「〜という形になります」「〜となっております」
- 「〜については」の乱用

**空虚な形容**
- 「適切に」「効率的に」「柔軟に」「シームレスに」
- 「包括的」「堅牢」「最適な」「強力な」

**具体物を隠す比喩**
- 「履歴の窓」「〜の地図」「〜の旅」（→「直近N件の履歴」「〜の一覧」など、指している物をそのまま書く）
- 「〜が太る」「〜が効く」（→「〜が増える」「〜が長くなる」「〜が有効になる」「〜が働く」など、何がどう変わるかをそのまま書く）
- 「〜が〜に化ける」（→「〜が〜になる」「〜が〜に置き換わる」「〜が〜として記録される」など、変化の前後と経路をそのまま書く）
- 「無音」「無音で〜する」（→「ログを出さずに」「エラーを返さずに」「警告なしに」など、何が出ないのかをそのまま書く）
- 「〜の箱」「〜を入れる箱」（→「〜のテーブル」「〜の構造体」「〜のフィールド」「〜のキュー」など、指している物をそのまま書く）

**作業実況**
- 「まず〜し、次に〜し、最後に〜しました」
- 「〜を確認しました。その結果〜」

**構文の癖**
- 「単に〜ではなく、〜なのです」
- 「〜こそが、〜の本質です」

**Before**

> 承知しました。パフォーマンスの課題について包括的に調査を実施しました。まずログを確認し、次にDB設定を確認しました。重要なのは、接続プールの設定が適切でないという点です。プールサイズの拡大を行うことで、改善が可能かと思われます。何かあればお知らせください。

**After**

> 接続プールの上限10が小さすぎます。深夜帯にこれを超えて待機が発生していました。上限を30に上げれば解消しますが、コネクションリークの有無は未確認です。

## §5 書き終えたらのセルフチェック

- [ ] 1行目だけ読んで要点が伝わるか
- [ ] 80字を超えた文がないか。あるなら分割できないか
- [ ] 「〜を行う」「〜することができます」が残っていないか
- [ ] 「適切に」「効率的に」など、中身を書いていない語がないか
- [ ] 前置きと締めの定型句を消したか
- [ ] 断定と推測が書き分けられているか。未確認を断定していないか
- [ ] 見出し・箇条書きの先頭だけを拾って筋が通るか

## §6 やりすぎ防止

**短い応答に全原則を持ち込まない。** 最小の形は「一文の中で結論を先、理由を後」。一言で済む確認に見出しや箇条書きを被せない。

**正確さと読みやすさが衝突したら、正確さを取る。** 曖昧にして短くするのは、読みやすくなったのではなく情報が減っただけ。条件や例外が本質なら、文が長くなっても書く。

**削ってはいけないもの。** 実際の答え、破壊的操作の事前確認、想定と違う前提で進めた事実、失敗した事実。これらは定型クッションではない。

**リズムを均一にしない。** 全部を短文にすると、かえって読みにくい。長短を混ぜる。

## §7 `structured_output` との使い分け

| 状況 | 使うもの |
| --- | --- |
| 一問一答、短い報告、コミットメッセージ、Slackの返信 | このskillだけ |
| 論点が複数あり、並べ方の設計が要る | このskill ＋ `structured_output`（ピラミッド構造） |
| 保存・共有・後で読み返す成果物（調査レポート、分析、変更サマリ） | このskill ＋ `structured_output`（ピラミッド＋HTML出力） |

`structured_output` は「何をどの順で並べるか」、このskillは「一文をどう書くか」を扱う。層が違うので併用する。
